Teacher Email Settings

現在九封信全由系統代老師決定何時寄、寄給誰。這份提案把其中值得交給老師的部分開放出來，同時守住「老師不動設定，一切照舊」。

基準：DAHUA AI Email Templates（九封信、觸發、參數） 前端：dahua-dash origin/develop@96d64382 · app/dashboard/users/edit（基準 profile.html）、sections/assignments 後端：commerce-api src/email/brevo/、cron

1. 現況：誰觸發、誰收、老師能不能改

九封信依「觸發來源」分成三類，這個分法決定了哪些該開放、哪些不該。

三類的處理方式不同：

  • 系統事件（12、13、22）：一次性或跟帳號綁在一起，只給 22 一個開關就夠。
  • 老師動作（14、15、48、49）：老師已經「在做那件事」，設定應該長在動作旁邊，而不是藏在設定頁。
  • 排程（17、59）：最需要開放的一類，但 59 寄給學生、跨老師跨班，不能讓單一老師關掉。
前端目前的缺口 dahua-dash 沒有任何通知設定頁；Account 選單只有 Profile。派作業（assign-practice.js）和留評語流程裡沒有「要不要寄信」的選項。48／49 的 Remind 已經在三個地方：Teacher Dashboard 的 Active assignments 列（展開後一顆 Send reminder，一次寄給整列未交的學生，前端只有 3 秒 cooldown）、Students 頁的學生明細（一人一顆 Remind）、Word Game 頁（一人一顆，可改訊息）。後端不去重，按兩次寄兩封，程式註解寫明是刻意的。

2. 設計原則

  1. 預設值等於今天的行為。老師一個設定都不碰，寄信結果和現在一模一樣。開放設定不能變成「多一步才會寄」。
  2. 分兩層講：「我收什麼」和「我的學生收什麼」。老師對自己信箱的控制是完全的；對學生信箱的控制是代理，要有邊界。頁面上用綠／藍兩色帶一路區分。
  3. 設定長在動作旁邊，設定頁只是總覽。派作業時勾「Email students」，留評語時勾「Notify」，Remind 旁邊設自動規則；設定頁存的是這些勾選的「預設值」。
  4. 老師設規則，不改文案。Brevo 模板仍是唯一來源。老師能改的是「寄不寄、何時寄、寄給誰」，加上 49 已有的自訂訊息欄位。
  5. 不能讓學生被轟炸。任何自動規則都有系統上限，跨老師合併計算。

3. 三個方案

差別在「開放到哪一層」。三案都以同一頁設定頁為底，B 和 C 往上疊。

方案 A

設定頁，老師層級

  • Profile 多一個 Notifications 分頁
  • 17：開關、寄送時間、只在有人未交時寄
  • 22：開關
  • 14／15：Always／Ask each time／Never
  • 48／49：維持手動
前端一頁、後端一個 preferences 欄位、cron 17 讀設定。最快能上。
方案 B建議

A ＋ 動作旁的設定 ＋ 自動提醒

  • A 的全部
  • 派作業對話框、留評語各長出對應的 inline 控制
  • 48：自動提醒規則（到期前 n 天、逾期後 n 天、最多幾次）
  • Dashboard 那一列的改動（Reminded n ago）另開一版
  • 系統上限：同一學生同一作業 24 小時最多一封
多兩個 inline 元件、一個 reminder cron。老師真正會用到的都在這裡。
方案 C

B ＋ 班級覆寫 ＋ 學校預設

  • B 的全部
  • 每個班可以覆寫老師的預設
  • 協調員／管理員設學校層級預設與上限
  • 學生自己的偏好（digest 時間、關閉）
  • Quiet hours、每週摘要
多一層 precedence 和權限。等 B 上線看老師實際怎麼調再決定。

建議走 B，把 C 的「班級覆寫」留成第二期。理由：A 的設定頁老師一年開不了幾次，真正的痛點是「派作業當下要不要吵學生」和「逾期了要一個一個按 Remind」，這兩件事只有 B 解。

6. 規則怎麼疊、怎麼防轟炸

優先順序

系統上限永遠生效，任何層級都改不掉
當次覆寫對話框裡的勾選、單一作業的自動規則
班級覆寫第二期
老師預設設定頁
系統預設＝今天的行為

左邊贏。老師預設只是在填「當次覆寫」時的初始值，而不是最終決定。

多位老師、多個班

  • 寄給學生的信（14、15、48、49）以那個作業的老師的設定為準。同一個學生在兩個班有兩位老師，就分別依各自的設定。
  • 59 digest 不受任何老師設定影響。
  • 17 只看收信老師自己的設定。

系統上限（防轟炸）

  • 同一學生、同一作業，24 小時內最多一封提醒，手動和自動合併計算。這一條改變現況：今天後端刻意不去重，按兩次寄兩封（見第 9 節第 4 條）。撞到上限時 Dashboard 怎麼顯示，不在這一版。
  • 自動提醒每個作業最多 4 封（到期前 1 ＋ 逾期後 1 ＋ 重複最多 2）。
  • 已繳交的學生立刻退出自動提醒序列。
  • 作業結束日（若有）之後不再自動提醒。
  • 寄送時間一律用學校時區；沒有時區資料時退回現在 cron 的固定時間。

8. 分期

Phase 1

設定頁 ＋ 派作業／評語 inline

  • Notifications 分頁（17、22、14、15，59 鎖定）
  • Assign 對話框的 Email students 勾選
  • 留評語的 Notify student 勾選
  • 17 cron 讀 sendAt／onlyIfOutstanding
Phase 2

自動提醒（規則與 cron）

  • 48／49 自動規則（設定頁 ＋ 單一作業覆寫）
  • ReminderLog 與 24 小時上限
  • Dashboard 作業列的 Set up 與 Reminded n ago（另開一版）
  • 17 的 combine 選項
Phase 3（方案 C）

班級覆寫 ＋ 學校預設 ＋ 學生偏好

  • All my classes 下拉變成可選單一班級
  • 協調員設學校預設與上限
  • 學生自己開關 59、選時間

9. 待確認

  1. PM59 digest 真的不給老師關？如果學校端要求「老師能關」，就得改成班級層級才不會互相蓋掉。
  2. PM14 的 Ask each time 值不值得做？如果多數老師只會選 Always／Never，這個選項可以砍掉讓設定頁更短。
  3. BackendSchool／Program 有沒有時區欄位？17 的 sendAt 和自動提醒的「n 天」都靠它。
  4. Backend手動 Remind 今天刻意不去重（按兩次寄兩封）。24 小時上限會改掉這個行為，要不要？要的話 ReminderLog 得在後端，前端的 3 秒 cooldown 不夠。
  5. Backend17 現在的 cron 固定幾點寄？那個時間就是設定頁的預設值，要寫在畫面上。
  6. DesignNotifications 放 Profile 分頁（本提案）還是 Account 選單獨立一項？Profile 分頁的好處是不動導覽；缺點是 users/edit 現在也被管理員拿來編別人的資料，要確定分頁只在「編自己」時出現。
