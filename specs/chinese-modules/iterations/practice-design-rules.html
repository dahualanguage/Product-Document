2 十條判準

R1 · 依「它改變什麼」分段，不依欄位來源

問一句：改了它，學生那邊什麼會不一樣？答案相同的收成一段。 Mirroring 分出來是 On screen（看得到什麼）／On play（聽得到什麼）／ Passing（什麼時候算過）。

反例：現行把 Audio Mode、Translation First、Display Settings、Auto Pass、 Audio Settings 五塊等重平鋪，順序是元件被寫進檔案的順序。

R2 · 模式不是設定

判準是學生端的畫面會不會整個換掉。會 → 提到最上面做成兩選一；不會 → 留在設定列。

Audio Mode 打開，學生端整片課文換成一張耳機卡（assignments/content/index.js 的 renderAudioModePanel）——那是換一種練習，不是換一個顯示偏好。 它會強制鎖住拼音／翻譯也就不奇怪了：純聽力底下本來就沒有「預先決定顯示什麼」這回事。

R3 · 控制項三選一

什麼樣的選項用什麼例
固定、≤4 個、每個兩三個字分段控制項（全部露出） Pinyin · Translation · Play the translation first
要聽過／看過才選得出來chip，點一下＝選它＋試它 Speed · Voice
資料驅動、長度未知下拉Project（專案清單會長）

不是「下拉一律不好」。 下拉的價值是「清單很長，先收起來」； 三四個兩字選項收起來沒省到空間，卻要兩次點擊、看不到有哪些、也沒辦法比較。

R4 · 「學生自己決定」一律講 Choice by student

產品裡同一個概念有三套機制：PINYIN_PREFERENCES.STUDENT_CHOICE、 SPEED_PREFERENCES.STUDENT_CHOICE、以及被 audioMode 覆寫。 畫面上要講同一句話，並排就看得出來——否則老師不知道為什麼有兩個會變灰、另外兩個不會。

R5 · 預覽與設定同一張卡

「設定面板 ＋ 旁邊一個預覽」那兩個一定會不一致。 現行的實例：純聽力模式下學生根本看不到句子，預覽卻照列五句、照顯示拼音。

改成同一張卡：上半是學生螢幕的真實排版，下半就是改它的控制項。它不可能跟自己矛盾。

R6 · 學生端排版照抄，不憑印象

出處是 src/sections/assignments/content/<type>/——最容易被忘記的一半。 Mirroring 抄出來才知道：拼音在字的上面；Choice by student 的翻譯 預設是收起來的（translationVisibility 初始 []，要點眼睛）。

這條是踩過兩次坑換來的。「發音嚴格度」和 Vocabulary 的「Examples 開關」 都是憑「這樣設計比較合理」推出來的，產品裡根本沒有。 看起來像設定、講得通、老師應該會想要——都不算證據。

R7 · 用字講老師關心的事，不講機制

現行改成
Max attempts before auto passMove on after 3 tries（原標籤講的是機制）
Translation FirstPlay the translation first ＋ Yes / No（是問句就用 Yes/No 答）
NO_PINYIN / STUDENT_CHOICEShown / Hidden / Choice by student（enum 值永遠不外露）
Optional — no emailsMandatory / Optional ＋ 各自寫清楚（原標籤在講副作用）

R8 · 只講例外，不覆述常規

整班就寫 all 5 students，不列名字；有人拿不到才把那個人與原因寫出來。 聲音的地區標籤只在「不只一組」時出現——只有一組時，標上語言只是把已經選好的專案語言再講一次。

R9 · 鎖定、衝突、空白都要給原因

純聽力下兩個下拉不是安靜地變灰，是換成一句「這裡沒有東西可以預先決定，由學生自己叫出來」。 學生已被別班派走 → 標 In Chinese 3B，而不是單純點不動。 對話類內容不能切句 → 在選專案的當下就講，不是等到下一步才跳警告。

R10 · 一個動作從頭到尾同一個字

觸發鈕 Assign to 2 classes → 對話框標題 Assign to 2 classes → 送出鈕 Assign。同一個動作換三個說法，讀的人會以為是三件事。

為什麼是這個形狀。 使用者的原話是「工作列」：上面是控制項、下面是學生的畫布，那它就該長得像貼在畫布頂上的工具列， 不是一張表單卡；「編輯欄位在上、學生預覽在下」，改哪個上面的格子，下面的卡跟著變（R5 的另一種寫法）。 兩行是因為六個控制項總寬約 1390px 本來就放不進一行，與其讓它自己換行，不如照它們影響的東西分兩行。 不 sticky（工具列只有 120px 高，不必貼著頂欄）。畫布不收合（2026-09-15 拿掉收合鈕）——它就是這一步的主體。

走過的岔路：三段眉標的 rows 卡（v3 第一版）→ 六列一張卡 → 兩欄三列 → 工具列。前三種都是「表單」，只有最後一種是「工具」。

Sentence Scramble

5 做法（附錄）

每一張卡都走同一套。這一段已經固化成 skill practice-iteration， 我在做下一張卡時會自動照著跑，這裡留一份給人看的版本。

  1. 先 fetch 再讀。 本地 checkout 會過期——這一版做到一半就發現落後 14 個 commit， 期間產品加了八種型別的 icon 對照表。git fetch origin develop 後用 git show origin/develop:<path> 讀，不動工作區。
  2. 兩邊都要讀。 老師端 src/sections/practice/view/unified/， 學生端 src/sections/assignments/content/。後者最容易被忘記，而它才看得出 「這東西是內容還是偏好」。
  3. 先做基準檔。 現行畫面的複刻，逐項照抄 sx 與 theme，不做自由發揮。 它是對照組——提案一旦跟它並排，改了什麼一目了然。基準檔不跟著提案改， 否則就沒有對照組了。
  4. 問題要有出處。 每一條都要指得到檔案與行為，不是「我覺得」。
  5. 每個視覺改動都截圖看過。 讀 CSS 不是驗證。這一版靠截圖抓到的自己的錯包括： class 名稱衝突、缺 disabled 樣式、兩行擠成一行、色票在這個底色上整個糊掉。
  6. 決策與更正都寫進 log。 包括寫錯又更正的—— 「我一度以為 X，實機截圖證明不是」比只留結論有用。
